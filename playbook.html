Quick start (about 20 minutes)

Follow these in order. Each step links to the full detail further down.

  1. Get access and secure your account Accept the invitation to the repo (check your email or GitHub notifications), then turn on two-factor authentication at github.com/settings/security. Two-factor is required for everyone.
  2. Install the tools Git, Visual Studio Code, and the current Node.js LTS. Details in section 2.
  3. Clone the repo and open it in VS Code
    terminal
    git clone https://github.com/kenziemw/Vow-Fare-Makenzie-Whitman.git
cd Vow-Fare-Makenzie-Whitman
code .
  4. Install dependencies and browsers
    terminal
    npm install
npx playwright install chromium
    This also installs the Git hooks that format and lint your code on every commit (section 7).
  5. Run the site locally
    terminal
    npm start
    Open http://127.0.0.1:5500. You should see the VowFare landing screen; click Set your budget and open a vendor to check all three screens work.
  6. Confirm your setup is healthy
    terminal
    npm run lint && npm run format:check && npm test
    All three should pass before you change anything. If one fails on a fresh clone, tell the team in chat; that is a bug in our setup, not in you.
  7. Ship something small Pick a card from Ready on the project board, create a branch, and open a pull request following section 4. Your first PR can be as small as adding yourself to the team list in this playbook.

1. Language selection

We use HTML5, CSS3, and vanilla JavaScript (ES2022). No framework, no bundler, no build step.

Node.js (current LTS) is used only for developer tooling such as ESLint and Playwright. It is never shipped to the browser.

Why this choice

  • The product today is a static, three-screen prototype. It lives in a single index.html with no server, database, or login, so git push is the whole deploy.
  • Nothing framework-specific to learn. Anyone who knows basic JavaScript can contribute on day one.
  • Plain code is easy to review. AI assistants write plain HTML, CSS, and JS reliably, and reviewers can read every line of the diff without knowing a framework.
  • Free hosting. GitHub Pages serves static files at no cost.

Alternatives we considered

OptionDecisionWhy
React with ViteNot yetAdds JSX, a bundler, and config for a three-screen mock-up. Adopt when we pass roughly five screens or need shared state that is hard to manage by hand.
TypeScriptNot yetValuable once the vendor-matching logic moves into its own module. That extraction is the trigger to migrate.
A backend (Node, Supabase, or similar)Not yetWe have no real vendor data, accounts, or bookings. When we do, the choice gets recorded as a short decision note in docs/decisions/.

Conventions

  • Two-space indentation, double quotes, semicolons. Prettier enforces this, so do not argue about it in review.
  • const by default, let when you must reassign, never var. Always ===.
  • camelCase for JavaScript, kebab-case for CSS classes and file names.
  • Colors, fonts, and spacing come from CSS custom properties declared in :root. Do not hard-code a hex value twice.
  • Use semantic HTML (button for actions, a for navigation, real headings) so keyboard and screen-reader users can follow the three-screen flow.
  • New code attaches events with addEventListener. The prototype still has some inline onclick handlers; migrate them when you touch the surrounding code.

3. Development strategy

Kanban with work-in-progress (WIP) limits, plus a short daily async check-in and a weekly planning and review.

We skip Scrum sprints because four teammates have uneven weekly availability around classes and deadlines. Continuous flow with WIP limits adapts to that better than a fixed two-week commitment.

The board

Five columns, left to right. A card only moves right when it meets the exit rule.

ColumnA card is here whenWIP limit
BacklogIt is an idea or an unrefined issue.None
ReadyIt meets the Definition of Ready below.8 cards
In progressOne person is assigned and a branch exists.2 per person
In reviewA PR is open and CI is running or green. A reviewer picks it up within 24 hours.4 cards
DoneThe PR is merged and the change is verified on the live URL.None

If a limit is full, help finish something already in flight (usually a review) before you start new work.

The weekly rhythm

WhenWhatLength
Every working dayPost in the team chat: what I finished, what I am doing next, what is blocking me.2 minutes
MondayPlanning. Pull cards from Backlog into Ready, assign owners, and agree on the week's goal.30 minutes
FridayReview and retro. Demo the live URL, then agree on one thing to change next week.20 minutes

If you are blocked for more than a day, say so in chat right away. A blocker that sits is the most expensive kind.

Definition of Ready

  • A user story: "As a couple planning a wedding, I want ___ so that ___."
  • Acceptance criteria written as checkable statements.
  • A link to the research or test finding that motivates it, so we build for evidence rather than opinion.
  • Small enough to finish in about a day. If not, split it.
  • A sketch or screenshot reference if it changes the UI.

Definition of Done

  • Every acceptance criterion is met.
  • lint, format:check, and test are green in CI.
  • At least one teammate other than the author approved the PR.
  • Merged to main by squash merge, and the issue closed automatically.
  • Verified on the live URL after GitHub Pages redeploys.
  • For UI changes, before and after screenshots are in the PR description.

A day in the life of one card

  1. Pick the top card in Ready, assign yourself, and drag it to In progress.
  2. Branch from the latest main using the naming rule in section 4.
  3. Make small commits with Conventional Commit messages. Run the checks before you push.
  4. Open a PR with Closes #N in the description. The card moves to In review automatically.
  5. Respond to review comments, push fixes, and wait for green checks.
  6. Squash and merge. Wait for Pages to redeploy, then check the live URL.
  7. Confirm the card landed in Done, and pick the next one.

4. Git strategy and controls

GitHub Flow. main is always deployable and is production. All work happens on short-lived branches that merge through reviewed pull requests.

Repo: github.com/kenziemw/Vow-Fare-Makenzie-Whitman

Branch naming

Use type/issue-number-short-summary, all lowercase, words separated by hyphens. Keep branches alive for two or three days at most.

examples
feature/14-empty-state-no-matches
fix/21-slider-resets-guest-count
docs/9-playbook-setup-steps
chore/3-add-eslint-and-prettier

Our first design revision was made on a branch (group-out-of-budget) and merged through a pull request, which is the pattern to follow for everything.

Commit messages

We follow Conventional Commits: type(scope): subject. Write the subject in the imperative mood, keep it under 72 characters, and skip the trailing period. Use the body to explain why, not what.

TypeUse it for
featA user-visible capability
fixA bug fix
docsREADME, playbook, comments
styleFormatting only, no behavior change
refactorCode change with no behavior change
testAdding or fixing tests
ci and chorePipelines, tooling, dependencies, config
good commit messages
feat(matches): group out-of-budget vendors into a separate section
fix(slider): keep guest count when switching categories
docs(readme): add before and after screenshots
chore(deps): add playwright and http-server

The commit-msg hook runs commitlint and rejects anything that does not follow this format (setup in section 7).

Review and approval controls on main

These are configured once as a branch ruleset (steps in section 9). They apply to everyone, including admins.

How to review a PR

  • Respond within 24 hours. Pull the branch or use the preview if you are unsure how it behaves.
  • Check the acceptance criteria first, then readability, then edge cases, then style. Prettier and ESLint already cover style.
  • Flag anything that looks like a secret, personal data, or an unvetted dependency as a blocker.
  • Prefix small suggestions with nit: so the author knows they are optional. Approve with comments when only nits remain.
  • Keep PRs small. Over roughly 400 changed lines, ask the author to split it.

5. Issue tracking

GitHub Issues for the work, a GitHub Projects board for the flow. Everything lives next to the code, so a PR can close its card automatically.

Working agreements

  • No work without a card. If you find something while working, open a new issue instead of widening your PR.
  • Every card has one assignee and one of the type labels below.
  • Write titles as outcomes in the imperative: "Show an empty state when no vendor fits the budget," not "Empty state bug."
  • Every PR contains Closes #N. Merging closes the issue and moves the card to Done.
  • On Monday we groom the Backlog: close stale cards, split large ones, and move ready ones up.

6. AI agents and controls

Approved: Claude (the claude.ai chat and Claude Code, see the docs) and GitHub Copilot in VS Code.

Everything else needs a team vote first. Propose the tool in chat, get approval from three of four teammates, and add it to this section before anyone uses it on project work.

ToolGood forNot for
Claude (chat)Brainstorming, drafting code and tests, explaining unfamiliar code, writing docs, reviewing a diff you paste inAnything containing secrets or personal data. Final architecture decisions without the team.
Claude CodeMulti-file changes on a feature branch, scaffolding config, fixing failing testsRunning on main. Merging. Holding admin or deploy credentials.
GitHub CopilotInline autocomplete, quick explanations, boilerplateWriting whole features unsupervised

Guardrails

  1. A human owns every line. If you cannot explain AI-written code in review, it does not get merged.
  2. AI code goes through the same pipeline as human code. Branch, pull request, green CI, and one human approval. Agents never push to main, never merge, and never get admin tokens.
  3. Keep secrets and private data out of prompts. That means API keys, tokens, .env contents, personal data, private vendor pricing, and unpublished interview recordings.
  4. Disclose AI use in the PR. The PR template has a checkbox for the tool and what it generated.
  5. Verify every dependency an AI suggests. Confirm the package exists on npmjs.com, is actively maintained, and passes npm audit. Invented package names are a known supply-chain attack.
  6. Keep the audit trail honest. When an agent produces a first draft, commit it as its own commit and make your human edits in later commits, so history shows what the machine produced and what we changed.
  7. Never present invented evidence as real. Vendor names, prices, and ratings in the prototype are illustrative mock data and are labeled that way. AI must not generate fake reviews, testimonials, quotes, or research results.
  8. Ask for small diffs. One issue at a time, with the acceptance criteria in the prompt. Review the diff, not just the result.
  9. Do not skip permission prompts. When using Claude Code, keep the default mode where it asks before editing files or running commands, and run it only on a feature branch.

8. Testing frameworks

Playwright Test (@playwright/test) for end-to-end tests. See the Playwright docs.

The product is a set of user journeys (landing, budget, matches, vendor profile), so we test it the way a couple would use it: in a real browser, clicking through the screens.

How testing fits the workflow

  • Locally: run npm test before you push. The pre-commit hook handles lint and format; tests are run on demand because they are slower.
  • In CI: the quality job runs the full suite on every pull request. A red check blocks the merge.
  • Definition of Done: any change to behavior comes with a new or updated test. A bug fix starts with a test that fails, then the fix that makes it pass.
  • By hand: UI changes also get a quick manual pass at phone width (Chrome DevTools device toolbar) and before and after screenshots in the PR.

Commands

npx playwright test --ui      # interactive runner, best for debugging
npx playwright show-report    # open the last HTML report
npx playwright codegen http://127.0.0.1:5500   # record a test by clicking

import { test, expect } from "@playwright/test";

async function setBudget(page, value) {
  await page.locator("#budget-slider").evaluate((el, v) => {
    el.value = String(v);
    el.dispatchEvent(new Event("input", { bubbles: true }));
  }, value);
}

test("a couple can go from the landing screen to a vendor and back home", async ({ page }) => {
  await page.goto("/");
  await page.getByRole("button", { name: "Set your budget" }).click();
  await expect(page.getByText("Fits your budget").first()).toBeVisible();

  await page.locator(".vendor-card").first().click();
  await expect(page.getByRole("button", { name: "Request to book" })).toBeVisible();

  await page.getByRole("button", { name: /Back to matches/ }).click();
  await page.getByRole("button", { name: /Back to home/ }).click();
  await expect(page.getByRole("heading", { name: /No connections/ })).toBeVisible();
});

test("a high budget fits every photography vendor and hides the outside-budget group", async ({ page }) => {
  await page.goto("/");
  await page.getByRole("button", { name: "Set your budget" }).click();
  await setBudget(page, 10000);
  await expect(page.locator("#match-count")).toContainText("8 of 8");
  await expect(page.locator("#out-section")).toBeHidden();
});

test("a low budget moves vendors into the outside-budget group", async ({ page }) => {
  await page.goto("/");
  await page.getByRole("button", { name: "Set your budget" }).click();
  await setBudget(page, 1500);
  await expect(page.locator("#out-heading")).toContainText("Outside this budget");
});

// Known gap found in user testing: a tester asked what happens when no vendor fits.
test.fixme("shows an empty state with a suggested minimum when no vendor fits", async ({ page }) => {
  await page.goto("/");
  await page.getByRole("button", { name: "Set your budget" }).click();
  await setBudget(page, 800);
  await expect(page.getByText(/no vendors fit/i)).toBeVisible();
});

What we do not have yet

There are no unit tests because the matching logic still lives inside the page script. When we extract it into src/matching.js we will add Vitest unit tests for it and record the change in docs/decisions/.

Product validation tests

Code tests tell us it works. We also test whether it is understood and wanted, using two measures on every round of prototype testing with prospective customers (not friends or family):

  • Comprehension: after a cold first look, can they say what it does and who it is for?
  • Likelihood to switch: a 1 to 10 rating of how likely they would be to use it instead of how they find vendors today, plus what holds the number back.

The latest round with five prospective customers averaged 8.8 out of 10. Every finding becomes a card on the board.

9. Other controls, tools, and procedures

Deployment is automatic: merging to main publishes the site on GitHub Pages at kenziemw.github.io/Vow-Fare-Makenzie-Whitman.

Because there is no server or database yet, our operational surface is small: Pages, Actions, and the repo settings below.

Deployment and rollback

  1. Merge a PR into main. GitHub Pages rebuilds, usually within one to two minutes. Watch the pages build and deployment run in the repo's Actions tab.
  2. Open the live URL in a private window and walk all three screens. Hard-refresh (Cmd or Ctrl plus Shift plus R) if you still see the old version.
  3. If something broke, use the Revert button on the merged PR to open a revert PR, or run git revert <commit-sha> on a branch. Never force-push to main.

Secrets and configuration

  • Today there are no secrets. The site is static and calls no APIs. Keep it that way as long as you can.
  • Never commit .env files, keys, or tokens. Commit a .env.example with fake values instead.
  • Anything placed in browser JavaScript is public. If we ever need a private key, it goes behind a serverless function, never in index.html.
  • When a CI secret is needed, add it under the repo's Settings, Secrets and variables, Actions and read it as ${{ secrets.NAME }}.
  • If a secret leaks: rotate it first, then remove it from the code, then tell the team. Deleting the commit does not un-leak it.
  • Two-factor authentication is required on every teammate's GitHub account.

Data and privacy

  • The prototype stores nothing. Budget and guest-count values live in the browser's memory and disappear on refresh.
  • The waitlist and contact forms open the visitor's own email app (mailto:). No server receives the data.
  • Vendor names, prices, and capacities are illustrative mock data.
  • Before we collect any real user data we need a short privacy notice and a decision on where it is stored. A tester already asked how data would be saved, so treat this as a launch blocker.

Incidents and the "on-call" steward

There is no pager for a static prototype. Instead, one teammate is the site steward each week, rotating through the team.

  • The steward opens the live URL every Monday and before any class demo, and walks all three screens.
  • If the site is down or wrong, open an issue labeled incident and post in chat. Check githubstatus.com in case it is a GitHub outage.
  • Fix forward or revert the same day. After a real incident, write three lines in the issue: what happened, why, and what we change.
  • Freeze main (no merges) for 24 hours before a graded demo, so the steward can verify a stable build.

Communication and documentation

  • Team chat is for quick async updates. Decisions that affect the code get written in the issue or PR so they are searchable.
  • The README is the source of truth for setup. This playbook is the source of truth for how we work, and it changes through pull requests like any other file.
  • Record significant technology choices as short notes in docs/decisions/ using three headings: context, decision, consequences.

One-time repo setup (maintainer)

The controls above only protect us once someone switches them on. Work through this list in order and tick each item.

  • Commit package.json, eslint.config.js, .prettierrc, .prettierignore, commitlint.config.js, .gitignore, and .husky/ (section 7)
  • Commit playwright.config.js and tests/journey.spec.js (section 8)
  • Commit .github/workflows/ci.yml, .github/dependabot.yml, .github/pull_request_template.md, and the issue template
  • Run the CI workflow once so the quality check name exists
  • Settings, Pages: deploy from branch main, folder / (root)
  • Settings, General, Pull Requests: allow squash merging only, and automatically delete head branches
  • Settings, Rules, Rulesets, New branch ruleset targeting main: require a pull request, 1 approval, dismiss stale approvals, require conversation resolution, require the quality status check and an up-to-date branch, require linear history, block force pushes and deletions, and leave bypass empty
  • Settings, Code security: enable Dependabot, CodeQL default setup, secret scanning, and push protection
  • Create the Projects board and labels, then paste the board URL into section 5
  • Invite every teammate and confirm two-factor authentication is on
